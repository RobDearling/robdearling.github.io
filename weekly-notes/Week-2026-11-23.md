### Data vs. Code

I've been thinking about when to expose systems as data rather than code. Here's an example.

**Code Approach**:

```hcl
locals {
  users = [
    {
      id                  = "emp001"
      display_name        = "Alice Jones"
      user_principal_name = "alice.jones@contoso.onmicrosoft.com"
    },
    {
      id                  = "emp002"
      display_name        = "Ben Smith"
      user_principal_name = "ben.smith@contoso.onmicrosoft.com"
    }
  ]
}

resource "azuread_user" "employee" {
  for_each = { for user in local.users : user.id => user }

  display_name          = each.value.display_name
  user_principal_name   = each.value.user_principal_name
  password              = var.initial_passwords[each.key]
  force_password_change = true
}
```

**Data Approach**:

```yaml
users:
  - id: emp001
    display_name: Alice Jones
    user_principal_name: alice.jones@contoso.onmicrosoft.com

  - id: emp002
    display_name: Ben Smith
    user_principal_name: ben.smith@contoso.onmicrosoft.com
```

```hcl
locals {
  users = yamldecode(file("${path.module}/users.yaml")).users
}

resource "azuread_user" "employee" {
  for_each = { for user in local.users : user.id => user }

  display_name          = each.value.display_name
  user_principal_name   = each.value.user_principal_name
  password              = var.initial_passwords[each.key]
  force_password_change = true
}
```

What is the right abstraction? Both approaches can work well, depending on the context.

* Do you need users to be able to modify this?
* If yes, do the users have access and knowledge to modify the code?

**The important one**:

* Do you need this to be represented in a way that would be inconvenient in data?

Are you limiting the capabilities of the implementation to make it easier to represent? a data-driven abstraction can look appealing at first, but edge cases may force you to add conditional logic for interpreting the data.

## Interesting Reads

### [Glue work is still harmful in the age of AI](https://www.seangoedecke.com/glue-work-is-still-harmful-in-the-age-of-ai/)

Sean argues that in the age of AI glue work becomes even more undervalued. I'd argue the opposite, whilst there is so much going on I think its useful for someone to stay grounded and join it all together. If no one steps in to take on the glue work processes will continue to fail.

Whether this gets recognised or not I think depends on the invidual and whether they are advocating their position and value in this work. If the organisation does not value it then simply stop doing it.

### [Most reviews should be approvals](https://seangoedecke.com/good-code-reviews/#most-reviews-should-be-approvals)

Interesting article as always from Sean Goedecke who states that most teams should favour approval rather than blocking a PR.

### [Vercel Agentic Boards](https://vercel.com/blog/introducing-vercel-board)

Vercel released an interesting concept named boards. The idea is a board where you can work with agents and agents can communicate with eachother and share context.

The idea is its effectively a messaging board to allow agents to communicate, delegate and provide information to eachother to support a goal.
